# Is there anything left to route? — 30 July 2026

A cross-tabulation of cheap-tier success against expensive-tier success, task by
task, to test one hypothesis: **the task set is too easy, so routing has nothing to
decide, and the experiment is measuring a difference that is near zero by
construction.**

Every number below was produced by running code in this repo on a scratch copy.
No model was called. No money was spent. The three real cache files and
`results.jsonl` are byte-identical to how this session found them. The script is
`routable.py`, committed alongside this file, so every figure re-derives with:

```bash
python3 routable.py --ladders all          # mock, all three ladders
ROUTER_MODE=replay python3 routable.py --real --ladders wide   # the paid run
```

---

## 0. The answer, before the working

1. **Asen's diagnosis holds, and the real data supports it at p ≈ 0.02.** On the
   ten tasks that have both a real cheap answer and a real expensive answer on
   disk, the cross-tab is `both succeed = 10, routable = 0, both fail = 0,
   inverted = 0`. Under the mock's own per-task success model, the probability the
   cheap rung goes 10-for-10 on those ten tasks is **0.0195**. The task set is
   easier than the repo assumes it is.

2. **But the ceiling cannot be stated as a number yet, and the mock cannot state
   it.** §6 is the finding that reframes everything: `difficulty_pct`, the single
   quantity the mock's success rate depends on, is a **rank within whatever tasks
   were sampled**, not a measure of absolute difficulty. Forty MATH500 level-1
   problems and forty MATH500 level-5 problems produce **identical** mock accuracy
   (60.0% cheap, 95.0% expensive, 35% routable, both). The mock is structurally
   blind to the exact hypothesis under test. Every mock routable fraction in §2 is
   a restatement of `MOCK_SKILL`, and worse, it moves the wrong way when the task
   set is genuinely hardened.

3. **The fix is a two-arm probe, and it costs $0.44.** The current pilot gate runs
   one arm and measures the wrong quantity. Running `always_cheap` *and*
   `always_expensive` over all 100 tasks on the `wide` ladder costs
   **$0.44** at the per-call prices this repo has already measured. That single
   number decides whether any further spending is worth anything, and it is the
   highest-value 44 cents in the project. **I have not run it.**

## 1. Method

For each task, two verdicts: did the cheap rung's greedy answer pass the grader,
and did the expensive rung's greedy answer pass. Four cells:

| cell | meaning | can routing win here? |
|---|---|---|
| `both_ok` | cheap right, expensive right | **No.** Every router scores 1. |
| `routable` | cheap wrong, expensive right | **Yes.** The only cell where escalating pays. |
| `both_fail` | cheap wrong, expensive wrong | **No.** Every router scores 0. |
| `inverted` | cheap right, expensive wrong | Perversely — escalating *loses* here. |

`both_ok` and `both_fail` are ties by construction: the best conceivable router
and the worst conceivable router score identically on them, so they contribute
exactly nothing to any accuracy comparison, at any sample size, forever. The
entire accuracy dynamic range of the experiment is

    ceiling = |routable| + |inverted|

Best possible router = `both_ok + routable + inverted`. Worst possible router =
`both_ok`. Everything the repo reports — `predictive`, `routellm`, `llm_router`,
`cascade`, `cascade_routing`, `random_matched`, the routing-skill table, the AUC
column — lives inside that interval.

Two data sources, kept apart because they disagree:

- **Real**: `cache/raw_calls.wide.jsonl`, 10 tasks with both a cheap and an
  expensive greedy answer, re-graded from the cached text. 5 math, 5 code.
- **Mock**: all 100 tasks, all three ladders. Deterministic, free, and — see §6 —
  not evidence about anything.

### 2.3 The two datasets disagree, and the disagreement is the finding

Mock says 26–30% of tasks are routable. Real says 0 of 10, with a 95% upper bound
of 27.8%. The intervals overlap, so this is not a contradiction — but it is
one-sided evidence, and it is stronger than the raw counts suggest, because the
mock makes a *per-task* prediction that can be scored:

| task | mock's p(cheap correct) | what really happened |
|---|---|---|
| code-805, code-86 | 0.821 | correct |
| math-105 | 0.779 | correct |
| code-244, code-252 | 0.684 | correct |
| math-92, math-407 | 0.663 | correct |
| code-475 | 0.635 | correct |
| math-331, math-473 | **0.534** | correct |

    P(cheap rung correct on all ten | the mock's own model) = 0.0195
    P(zero routable tasks in ten    | the mock's own model) = 0.0337

So the real cheap rung beat the mock's stipulation at **p = 0.020**, one-sided, and
the observed zero-routable outcome sits at **p = 0.034**. At n=10 that is as much
as this data can say, and it says the same thing twice.

## 3. The ceiling

Because `both_ok` and `both_fail` are ties, the maximum accuracy spread between
the best conceivable router and the worst conceivable router is `routable +
inverted`:

| dataset | ceiling | what it means |
|---|---|---|
| **REAL, wide, n=10** | **0.0 points**, 95% CI [0, 27.8] | Best possible router and worst possible router score **identically**. Not approximately — exactly. |
| MOCK, wide, n=100 | 30.0 points [21.9, 39.6] | stipulated |
| MOCK, claude, n=100 | 26.0 points [18.4, 35.4] | stipulated |
| MOCK, deepseek, n=100 | 22.0 points [14.2, 30.0] | stipulated |

On the only data that has ever touched a real model, **the ceiling is zero.** Every
policy in the repo scored 100% on that run, and §2.1 explains why that was not bad
luck: there was no cell in which any policy could have differed from any other.

The honest statement of the bound, since n=10 is small: **the real ceiling is
somewhere in [0, 27.8] points, point estimate 0.** That interval is too wide to
act on and too one-sided to ignore.

### 3.1 What a given ceiling demands in sample size

Every routing comparison is a paired binary comparison, so McNemar's exact test is
the relevant power calculation. Two thresholds: the easiest possible comparison
(a perfect router vs `always_cheap`, where all discordance runs one way), and a
realistic one (a good router capturing 70% of the routable band vs a weak one
capturing 30%).

| routable fraction | ceiling | n to pin the fraction to ±5 pts | n for perfect-vs-cheap, p<0.05 | n to detect a 40%-of-band router gap |
|---|---|---|---|---|
| 2% | 2 pts | 31 | 300 | **960** |
| 5% | 5 pts | 73 | 120 | **384** |
| 10% | 10 pts | 139 | 60 | 192 |
| 15% | 15 pts | 196 | 40 | 128 |
| 20% | 20 pts | 246 | 30 | 96 |
| 26% | 26 pts | 296 | 24 | 74 |
| 30% | 30 pts | 323 | 20 | 64 |
| 40% | 40 pts | 369 | 15 | 48 |

Read the last column as the real requirement. At a 30% routable fraction the
project needs 64 tasks to separate two routers — it already has 100, and 787
available. At a 5% routable fraction it needs 384; at 2%, 960. **The task set,
not the sample size, is the binding constraint, and no amount of the latter fixes
the former.** If the real routable fraction is a couple of points, a 787-task paid
run buys a table of ties, exactly as the 5-task run did.

## 4. The fourth cell — cheap succeeds, expensive fails

Observed `inverted` counts: **real 0/10** (uninformative, since cheap got
everything right); mock `wide` 0/100, `claude` 0/100, `deepseek` **1/100**.

The mock's near-zero inverted rate is **not a measurement, it is a constant**.
`models.MOCK_FAILURE_CORRELATION` blends a shared per-task latent draw with a
tier-specific one, and at the repo's chosen 0.75 the failures become nested, which
makes inversion arithmetically almost impossible. Sweeping it, with the mock cache
disabled:

| MOCK_FAILURE_CORRELATION | both_ok | routable | both_fail | **inverted** | ceiling |
|---|---|---|---|---|---|
| 0.00 | 56 | 32 | 2 | **10** | 42% |
| 0.25 | 65 | 31 | 0 | **4** | 35% |
| 0.50 | 71 | 26 | 1 | **2** | 28% |
| **0.75 (repo setting)** | 67 | 30 | 3 | **0** | 30% |
| 0.90 | 65 | 31 | 4 | **0** | 31% |
| 1.00 | 64 | 29 | 7 | **0** | 29% |

So the mock cannot produce non-monotonicity at its current setting, and its
"inverted = 0" carries no information about whether real models are monotone.

Why the cell matters. On objectively graded tasks, a non-empty `inverted` cell is
either genuine non-monotonicity (the cheap model is actually better on some task
type, which happens and is interesting) or grading/sampling noise. Either way it
**subtracts from what routing can achieve**, because a router that escalates a
task in this cell converts a correct answer into a wrong one. A cascade with a
perfect verifier is immune — it accepts the cheap answer and never escalates — but
a predictive router is not. This is a mechanism by which the cascade could beat
predictive routing for a reason that has nothing to do with the verifier-quality
story the repo is built to tell, and it is currently invisible because the mock
sets it to zero.

**Recommendation:** report the inverted cell on every real run, and treat a value
near zero with suspicion rather than satisfaction. Two greedy samples from two
different providers agreeing perfectly on a 300-task set would be more surprising
than a 3–8% inversion rate.

### 4.1 A cache-key bug found while doing this

The sweep above only moves when `ROUTER_CACHE=0`. With the mock cache warm, all
six rows are identical. `response_cache.make_key` includes `mock_seed` but **not**
`MOCK_SKILL` or `MOCK_FAILURE_CORRELATION`, so editing either constant silently
has no effect on a warm mock cache — a stale response is returned instead. Anyone
tuning the mock would get results from the previous constants and not be told.
Fix: fold the mock's behavioural constants into the key, or bump `MOCK_SEED`
whenever they change.

## 5. Signal versus noise in the oracle-minus-always-cheap gap

The headline gap in `run_eval.py`'s report, mock `wide` eval split (n=51):
`always_cheap` 72.5%, `oracle` 98.0%, **gap 25.5 points**.

That gap is not an estimate of anything with independent content. It **is** the
routable count, exactly: 13 tasks out of 51. Verified — the oracle's full action
space includes majority-of-5 over cheap samples on math, and on this split that
action rescues **0 additional tasks** beyond what greedy tier routing already
reaches. So:

| component | mock wide, n=51 | mock claude, n=51 |
|---|---|---|
| gap = routable tasks | 13/51 = **25.5%** | 11/51 = **21.6%** |
| binomial SE | 6.1 pts | 5.8 pts |
| 95% CI | [13.5%, 37.5%] | [10.3%, 32.9%] |
| extra from self-consistency action | 0 tasks | 0 tasks |

Three separate answers to "how much is real":

1. **Sampling noise alone is half the point estimate.** ±12.0 points around 25.5.
   Even taking the mock entirely at face value, the gap is `25.5 ± 12.0`.
2. **The measured component is zero.** None of the 25.5 points comes from a model.
   It is a deterministic function of `MOCK_SKILL` and `difficulty_pct`, and §6
   shows `difficulty_pct` does not encode task difficulty in the first place.
3. **The real-data bound brackets zero.** 0/10 routable, 95% upper bound 27.8%.

So: of a 25.5-point printed gap, **0 points are measured, ±12 points is the noise
floor at n=51, and the only real evidence puts the whole quantity between 0 and
27.8 points with a point estimate of 0.** The gap should not be quoted at all
until the two-arm probe in §9 has been run.

## 6. Why the mock cannot answer this question — the structural finding

`build_taskset.add_difficulty_pct` ranks tasks **within domain, within the sampled
set**, and stores the result as a 0–1 percentile. `models._mock_call` computes
`p_correct = base − spread × difficulty_pct`. So the mock's success rate depends
on a task's **rank among its neighbours in `taskset.jsonl`**, not on anything
about the task.

The consequence is that the percentile distribution is approximately uniform on
[0, 1] no matter which tasks are chosen. Demonstrated directly — forty tasks drawn
entirely from a single MATH500 level, same pipeline, same mock, five levels
spanning the benchmark's whole range:

| MATH500 level | difficulty_pct values assigned | mock cheap acc | mock exp acc | mock routable |
|---|---|---|---|---|
| 1 (easiest) | {0.5} | **60.0%** | 95.0% | 35.0% |
| 2 | {0.5} | **60.0%** | 95.0% | 35.0% |
| 3 | {0.5} | **60.0%** | 95.0% | 35.0% |
| 4 | {0.5} | **62.5%** | 95.0% | 32.5% |
| 5 (hardest) | {0.5} | **60.0%** | 95.0% | 35.0% |

Level 1 and level 5 are indistinguishable. The 2.5-point wobble at level 4 is seed
luck on 40 draws.

And it is not merely uninformative, it is **actively misleading**. Rebuilding the
task set with `MIN_MATH_LEVEL = 5` — the exact fix `STATUS.md` §4 recommends for a
too-easy task set:

| | mock cheap acc | mock routable | verdict |
|---|---|---|---|
| current set (`MIN_MATH_LEVEL=3`), wide | 67.0% | **30.0%** | |
| level-5-only, wide | **77.0%** ↑ | **21.0%** ↓ | *worse* |
| current set, claude | 71.0% | **26.0%** | |
| level-5-only, claude | **83.0%** ↑ | **15.0%** ↓ | *worse* |

Make the maths genuinely harder and the mock reports the cheap model getting
**better** and the routable fraction **shrinking**. The mechanism: collapsing to
one level collapses the percentile spread (every level-5 task ties, so all land at
0.5), which removes the hard tail where the mock generates most of its routable
tasks.

Three things follow, and they are the practical core of this document:

1. **No task-set change can be evaluated in mock mode.** Not this one, not any.
   The gate reading of "29.0%, IN BAND" on the n=100 mock probe is not a statement
   about the task set.
2. **The by-level table in §2.2 (level 5 → 41.7% routable) is circular** and must
   not be used to argue for stratifying on level. It says level-5 tasks rank high
   *within the current mixed set*, which is true by definition.
3. **`difficulty_pct` is also the wrong feature for the mock even in principle.**
   A tier's absolute capability against a fixed benchmark is what routing turns
   on. If the mock is to be kept, it needs an absolute difficulty anchor — real
   per-tier pass rates measured once and stored on the task — not a rank.

## 7. What the task set should look like

### 7.1 What is already on disk

| source | items | difficulty metadata | usable |
|---|---|---|---|
| `data/math500.jsonl` | 500 | **`level` 1–5**: 43 / 90 / 105 / 128 / **134** | 367 at level ≥ 3; 262 at ≥ 4; 134 at level 5 |
| `data/sanitized-mbpp.json` | 427 | **none at all** | 420 after dropping task_id ≤ 10 |
| **total** | | | **787** |

The 787 figure is right. But the two halves are in very different positions.

**MATH500 ships a real difficulty label and it is free to use.** Level 5 alone is
134 items; levels 4–5 give 262. Restricting to it costs nothing and requires no
download. Whether it is *enough* is the open question — the real cheap rung solved
both level-5 problems it saw, with unanimous samples, so the honest prior is that
level 5 helps but does not fix it.

**MBPP ships no difficulty signal whatsoever.** The only proxy in the repo is
`len(reference_solution.splitlines())`, which `build_taskset.py` itself flags as
unavailable before answering. Its distribution is short and thin: 211 of 420 items
have a 2–4 line reference solution, only 91 have ≥ 8 lines and 65 have ≥ 10.
Filtering on it yields at most ~90 tasks from a weak proxy — solution length is a
poor predictor of *model* difficulty, since a 3-line solution can encode a subtle
insight and a 15-line one can be mechanical.

That matters because **the code half carries the entire verifier-quality
experiment** — it is the domain with the free perfect verifier, and
`sweep_degraded.py` runs there and nowhere else. A code half with a 2-point
ceiling does not merely weaken the headline; it removes the repo's single best
result.

### 7.2 What 2026 says about these two benchmarks

Both are named as saturated, and MBPP specifically as saturated *for exactly the
model class this repo puts on the bottom rung*:

- **MBPP**: frontier models score 97%+ pass@1. "By 2026 it is only useful for
  testing smaller models (7B–30B range) where there is still meaningful
  separation, or for quick regression testing." DeepSeek v4-flash and Haiku 4.5
  are well above that class. **MBPP has to go.**
- **HumanEval**: 96–98%, same story. Not a substitute.
- **MATH500**: "essentially saturated, with frontier models scoring 95%+", though
  it is still cited as one of the few competition sets showing *some* separation.
  AIME and HMMT are at 95–99% and described as effectively solved.

### 7.3 Concrete replacements, constrained by this repo's own rules

The binding constraint is `graders.py`: no LLM judge, ever. That rules out most
open-ended benchmarks and leaves executable tests and exact-match answers.

**Code — replace MBPP.**

| candidate | size | grading | fit |
|---|---|---|---|
| **LiveCodeBench** (v6) | 1000+ problems, tagged Easy / Medium / Hard, with release dates | executable tests | **Best fit.** Anti-contamination is structural: problems are drawn post-training-cutoff. The Easy/Medium/Hard tags give a real stratification variable, which is exactly what MBPP lacks. Take Medium+Hard. |
| **BigCodeBench-Hard** | ~148 tasks, selected for solve rate < 50% | executable tests | Good, but small — 148 tasks is near the n=128 floor in §3.1 with no margin. Useful as a supplement. |
| SWE-bench Verified | 500 | repo harness | **No.** OpenAI's own audit found frontier models reproducing gold patches verbatim, and it needs a container harness this repo does not have. |

One calibration point worth having: on LiveCodeBench's hard subset a cheap fast
model was reported around 35%, and Haiku far lower. A 35% cheap pass rate against
a much higher frontier rate is close to the middle of the routable band. The
*hardest* subset may overshoot into `both_fail`, which is why Medium+Hard rather
than Hard alone.

**Maths — stratify first, then decide.**

| candidate | size | grading | fit |
|---|---|---|---|
| **MATH500 level 5** | 134 on disk | exact match | **Do this first — it is free.** Not because it will be sufficient, but because it costs $0 and the two-arm probe (§9) prices out the answer either way. |
| **Omni-MATH** | olympiad level | exact match | Strong candidate. Reported at ~60% for a small reasoning model and ~36% for open-source models — a cheap-tier pass rate in the 35–60% range is squarely in the routable band. |
| **HARP**, hardest bracket | 197 | exact match | Similar profile, reported around 41% for a small reasoning model. Small but usable. |
| IMO-level sets / FrontierMath | — | exact match | **Too hard.** Top models below 40% on IMO 2025; FrontierMath is far below that. These fill `both_fail`, which is just as useless as `both_ok`. |

The failure mode to avoid is over-correcting. `both_fail` is not better than
`both_ok` — a router cannot win there either. The target is the middle.

### 7.4 The target

**Aim for a routable fraction of 25–40%, with a hard floor of 15% and a hard
ceiling of 45%.**

Justification from §3.1, not from taste:

- At **30%**, 64 tasks separate a good router from a weak one, and ~320 pin the
  fraction itself to ±5 points. Both are affordable — 787 tasks are on disk and
  the probe costs single dollars.
- At **15%**, the same comparison needs 128 tasks. Still affordable, hence the
  floor there rather than higher.
- Below **15%**, the requirement passes 200 tasks and climbs fast; below 5% it
  passes 384 and the project stops being fundable at portfolio scale.
- Above **45%**, `always_cheap` is failing on nearly half the set and stops being
  a credible baseline; the cascade escalates most tasks so its fixed costs
  dominate, and the comparison degenerates in the opposite direction.

A useful secondary target: **keep the rescue rate above ~70%**. If the expensive
rung only fixes half of what the cheap rung misses, hardening the task set is
adding `both_fail`, not `routable`, and the ceiling stops rising.

### 7.5 Recommended composition

Keep both domains, keep the calibration/eval split, keep the perfect verifier on
the code half. Target ~400 tasks:

| slice | n | source | role |
|---|---|---|---|
| code, hard | 150 | LiveCodeBench Medium+Hard, post-cutoff | primary code half; carries the verifier experiment |
| code, easy control | 40 | MBPP, kept deliberately | anchors `both_ok`; proves the cross-tab moves with difficulty |
| maths, hard | 134 | MATH500 level 5 (on disk, free) | primary maths half |
| maths, harder | ~60 | Omni-MATH or HARP hard bracket | reaches further up if level 5 proves too easy |
| maths, easy control | 20 | MATH500 level 3 | anchors `both_ok` |

The controls are not padding. Without a slice known to be easy and a slice known
to be hard, a flat cross-tab cannot be distinguished from a broken grader — which
is precisely the ambiguity the current 10-for-10 real run leaves open.

**And fix `difficulty_pct` at the same time.** Replace the within-set rank with an
absolute difficulty field carried by the task (benchmark difficulty tag, or a
measured per-tier pass rate stored once). Without that, the mock stays blind, the
stratification cannot be checked offline, and §6 recurs on the next task set.

## 8. The pilot gate

### 8.1 What it does now

It measures **P(cheap rung fails)**. It once printed `GOOD — in the 30-40% target
band`; the current code widens that to two named constants,
`FAILURE_RATE_FLOOR = 0.20` and `FAILURE_RATE_CEILING = 0.55`, prints a 95% CI
with a rule-of-three correction, and refuses to rule when the interval straddles a
boundary. That was a real improvement and it should stay.

### 8.2 It measures the wrong quantity

    P(cheap fails)  =  routable  +  both_fail

The gate sees the sum and cannot see the split. A task set where the cheap rung
fails 40% of the time and the expensive rung fixes **none** of it passes the gate
cleanly and is worth precisely nothing. This is not hypothetical: on the mock's
own `deepseek` ladder the rescue rate is **63.6%**, so a 33% failure rate
corresponds to only a 21% routable fraction — and the gate reports the 33%.

The gate exists to catch "nothing to route". It measures a quantity that is an
**upper bound** on "something to route", and the slack in that bound is exactly
`both_fail`, which is the failure mode a *too-hard* task set produces. So the gate
is weakest on one of the two failures it was built to detect.

### 8.3 Is 30–40% the right band?

**As a failure-rate band, no — it is the right band for the wrong variable.** Map
it through the observed rescue rates:

| rescue rate | a 30–40% failure rate implies a routable fraction of |
|---|---|
| 95% (mock, wide maths) | 28.5% – 38.0% |
| 90% (mock, wide overall) | 27.0% – 36.0% |
| 64% (mock, deepseek) | 19.2% – 25.6% |
| 40% (a plausible hard-set value) | 12.0% – 16.0% — **below the floor** |

At high rescue rates 30–40% failure lands neatly inside the 25–40% routable target
in §7.4, so the band was well chosen *given an assumption the gate never checks*.
At low rescue rates the same reading passes the gate while the experiment has no
dynamic range. The band is not wrong so much as conditional, and the condition is
unmeasured.

### 8.4 What the gate should test

**Yes — it should test routable fraction.** That is the quantity it actually cares
about, it is the thing the ceiling equals, and it is the thing that decides
whether to spend.

Implemented in `routable.py`, with `ROUTABLE_FLOOR = 0.15` and
`ROUTABLE_CEILING = 0.45`, matching §7.4. It keeps everything good about the
current gate — named constants, printed band, Wilson interval, refusal to rule
when the interval straddles — and adds:

- the four-cell cross-tab, so `both_fail` is visible rather than folded in;
- the **rescue rate**, which says whether harder tasks would help or just add
  `both_fail`;
- exact McNemar on the discordant pair, which is the significance test for
  "`always_expensive` beats `always_cheap`" — the strongest accuracy claim the
  task set could ever support, and a hard upper bound on every other comparison;
- the per-domain and per-level breakdown, since the halves can fail in opposite
  directions.

Current readings from it:

```
mock:wide        IN BAND      routable 30.0% [21.9%, 39.6%]   (n=100, stipulated)
mock:claude      IN BAND      routable 26.0% [18.4%, 35.4%]   (n=100, stipulated)
mock:deepseek    UNRESOLVED   routable 21.0% [14.2%, 30.0%]   (n=100, stipulated)
real:wide        UNRESOLVED   routable  0.0% [0.0%,  27.8%]   (n=10)
```

The real row is the honest one: at n=10, `UNRESOLVED`, leaning too easy.

### 8.5 The cost objection, and why it does not bite

The one-arm gate is cheap because it only runs the bottom rung. The two-arm gate
runs the top rung too, and on the `wide` ladder that rung costs **72×** as much
per call — $0.004365 against $0.000061, both measured from the real cache. So the
gate goes from about $0.01 to $0.44 for 100 tasks.

Forty-three cents, once, to know whether a $1.50-per-ladder run and every
conclusion drawn from it means anything. **Keep the one-arm rate as a fast screen
— it still catches the extreme cases — and make the two-arm routable fraction the
gate that authorises spending.**

## 10. Summary

Asen's diagnosis is right, and the data in the repo already backs it rather than
merely suggesting it. Ten tasks have been answered by both a real cheap model and
a real expensive model. On all ten, both models got it right. There is no task in
that set where the choice of model changed the outcome, which means the best
possible router and the worst possible router would have scored exactly the same,
and every routing number the run produced was a tie that had to happen. The cheap
model, DeepSeek's flash tier at six thousandths of a cent per task, solved both of
the hardest maths problems it was given — MATH500 level 5 — and when it was
sampled four more times at high temperature on each maths problem, it returned the
same correct answer twenty times out of twenty. That is not a model being stretched.

How bad is the ceiling. On the real data it is zero points, with a statistical
upper bound of about 28 points because ten tasks cannot rule out more. The point
estimate is zero and the evidence leans hard that way: under the repo's own
simulated model of how often the cheap tier should fail, the chance of it going
ten-for-ten on those particular tasks is about 2%. The 25.5-point gap the repo
currently prints between its oracle and its always-cheap baseline is not a
measurement at all — it is thirteen simulated tasks out of fifty-one, it carries
a sampling error of plus or minus twelve points even on its own terms, and the
only real data bounds the same quantity between zero and twenty-eight.

There is a second problem underneath the first, and it is worse in a way, because
it means the repo cannot currently check its own work. The simulator's notion of
how hard a task is turns out to be a task's rank among the other tasks in the same
file, not anything about the task. Forty of MATH500's easiest problems and forty
of its hardest produce identical simulated results — sixty percent cheap accuracy
in both cases. So no change to the task set can be evaluated without spending
money, and the obvious fix points the wrong way: rebuilding with only the hardest
maths makes the simulator report the cheap model getting *better*, from 67% to
77%, and the routable share shrinking from 30% to 21%. Any offline verdict on a
new task set is therefore worthless, including the reassuring "29%, in band" the
pilot gate currently prints.

What to change. MBPP has to go: by 2026 it is saturated above 97% for frontier
models and is described as useful only for models in the 7-to-30-billion range,
far below the tier this project puts at the bottom of its ladder. That matters
more than it sounds, because the code half is where the free perfect verifier
lives and where the whole verifier-degradation experiment runs. Replace it with
LiveCodeBench's Medium and Hard problems, which are drawn from after each model's
training cutoff, come with real difficulty tags, and are still graded by executing
tests, so nothing about the repo's no-LLM-judge discipline has to change. For
maths, restrict MATH500 to level 5 first because that is free and already on disk,
and be ready to add an olympiad-level set such as Omni-MATH or HARP's hardest
bracket if level 5 turns out to be insufficient, which the real data suggests it
may. Keep a small deliberately easy slice of each so a flat result can be told
apart from a broken grader. Aim for a routable fraction between 25 and 40 percent,
and treat 15 percent as the floor below which no affordable sample size rescues
the experiment.

Finally, the pilot gate. It was the right idea aimed at the wrong number. It
measures how often the cheap model fails, but that figure is the sum of the tasks
routing can win and the tasks nobody can win, and the gate cannot see the split. A
task set where the cheap model fails 40% of the time and the expensive model fixes
none of it passes cleanly and is worth nothing. It should test the routable
fraction directly, which requires running the expensive tier as well as the cheap
one. That is the only real cost of the change, and on the widest ladder it takes
the gate from about a penny to forty-four cents for a hundred tasks. Forty-four
cents to find out whether everything downstream of it means anything is the best
value available in this project, and it should be spent before anything else is.
