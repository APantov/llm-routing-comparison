---

## 1. What the project is

A measurement project, built as a CV/portfolio piece, comparing two LLM
cost-saving architectures on the same 100 tasks:

- **Predictive routing** — inspect the query, guess difficulty, commit to one
  model. Pays once, silently misroutes.
- **Cascade routing** — call the cheap model, verify the answer, escalate on
  failure. Never misroutes an easy query, double-pays on every escalation.

The framing in `cascade_routing_project_plan.md` (v2.0, 29 July) is explicit
that "does routing work" is settled and not the question. The question is where
the crossover is.

**The manipulated variable is verifier quality, not router quality.** That is
the actual contribution and it is what makes the task set the way it is:

| domain | source | grading | runtime verifier |
|---|---|---|---|
| math | MATH500, levels 3–5, n=60 | exact match on normalised answer | **proxy** — self-consistency over k cheap samples |
| code | sanitized MBPP, n=40 | execute the shipped asserts | **free and perfect** — just run the tests |

Same cascade architecture, two verification regimes, one task set. No
LLM-as-judge anywhere — every task is graded deterministically, which
`graders.py` states is "the single biggest reason the task domains were chosen
as they were."

Five policies: `always_cheap`, `always_expensive`, `predictive`, `cascade`,
`oracle`. Planned deliverable is a cost-quality Pareto plot plus a second figure
splitting the cascade by domain.

## 2. Structure

Flat, six Python modules, no package, no `src/`, no tests directory.

```
build_taskset.py ──> taskset.jsonl ──┐
   reads data/math500.jsonl          │
        data/sanitized-mbpp.json     │
                                     v
sanity_check.py <───────────────  run_eval.py ──> results.jsonl
   (grader smoke test)                 │
                                       ├── policies.py ── graders.py
                                       └── models.py (mock | real)
```

### `build_taskset.py` (192 lines) — task set construction

`load_math500()` keeps levels ≥ `MIN_MATH_LEVEL = 3`; `load_mbpp()` reads the
427-item sanitized set and skips `task_id <= 10` (MBPP's canonical few-shot
examples). `add_difficulty_pct()` converts each domain's raw difficulty proxy
into a within-domain 0–1 percentile with ties sharing a mid-rank — necessary
because math has only three distinct levels across 60 tasks.
`stratified_sample()` takes equal counts from four difficulty buckets.
`SEED = 20260728`, `N_MATH = 60`, `N_CODE = 40`.

The leak discipline here is the notable part. Each task carries two separate
difficulty fields:

- `difficulty_proxy` — MATH500 `level` for math, **reference-solution line
  count** for code. The code one is a leak; it is used only for stratification
  and by the mock.
- `predict_features` — `{level, prompt_chars}` for math, `{prompt_chars,
  n_asserts}` for code. This is the only field `predict_is_hard` is allowed to
  read.

Splitting them into separate fields (rather than leaving a comment) is what
stops the leak being reintroduced by someone reaching for the handy value.

### `graders.py` (172 lines) — deterministic scoring

`_last_boxed()` is brace-matched rather than regex-matched, so
`\boxed{\frac{1}{2}}` parses correctly. `normalize_math_answer()` collapses only
universally-equivalent notation (`\dfrac`→`\frac`, `\left`/`\right`, `^\circ`,
`\text{}`, thousands separators, leading zeros) and deliberately does **not**
attempt algebraic equivalence — `1/2` and `0.5` stay distinct.
`grade_run_asserts()` writes candidate + setup + asserts to a tempfile and runs
it in a subprocess with `CODE_TIMEOUT_S = 10`. `extract_final_int` still exists
but is now dead code on this task set — the math grader is `exact_match_str`.

### `models.py` (323 lines) — the model client

Two backends behind one `call(tier, task, temperature, sample_idx)` signature.

**Model pair** (`MODELS`): cheap = `claude-haiku-4-5-20251001`, $1/$5 per MTok;
expensive = `claude-opus-5`, $5/$25. A 5× ratio. The docstring records why: the
cheap tier *must* accept `temperature` because `verify_math` samples it at 0.8,
and among current models only Haiku 4.5 still does; Sonnet 5 was rejected as the
expensive tier for the smaller ratio and for introductory pricing that runs to
2026-08-31. `_real_call` builds the request per-model — temperature only where
`accepts_temperature`, `thinking: {"type": "disabled"}` only where thinking is
on by default — because sending temperature to Opus 5 is a 400 and omitting
`thinking` silently turns it on.

**Mock**: `_draw()` seeds a `random.Random` from an MD5 of
`(MOCK_SEED, task_id, tier, temperature, sample_idx)`, so every mock outcome is
a pure function of its inputs with no global RNG state. Success probability is
`base − spread × difficulty_pct` per tier (`MOCK_SKILL`), blended with a shared
per-task latent draw at `MOCK_FAILURE_CORRELATION = 0.75` so the two tiers fail
on the same hard tasks.

`truncated_calls` is a module-level counter incremented when
`stop_reason == "max_tokens"`, because a truncated reply grades as *wrong*
rather than as an error.

### `policies.py` (278 lines) — the five policies, two verifiers

`Verdict(accepted, answer_text, cost_usd, latency_s)` is the contract between
verifier and cascade. `answer_text` exists specifically so `verify_math` can
hand back the plurality answer across its k samples rather than the greedy
sample it was given.

`verify_math` draws `SELF_CONSISTENCY_K = 5` samples (index 0 is the greedy call
already made, indices 1–4 at temperature 0.8), takes the plurality, and accepts
if agreement ≥ `AGREEMENT_THRESHOLD = 0.8`. The denominator is `len(answers)`,
not the parseable count, so unparseable samples count against agreement.

`predict_is_hard` is domain-aware: math routes on `level >= 5` (24/60 tasks),
code on `prompt_chars >= 100` (14/40). The docstring is honest about the
asymmetry — it reports the measured correlations of every candidate code feature
against reference-solution length and states that prompt length "is used because
it is the best of a bad set". I re-measured on the current taskset and the
numbers check out: `prompt_chars` r=+0.28, `words` r=+0.15, `n_asserts` r=−0.02.

### `run_eval.py` (241 lines) — runner and report

`provenance()` stamps `mode`, `mock_seed`, `k` and `agreement_threshold` into
every row of `results.jsonl`, so any slice of the file is self-describing and a
parameter sweep can be grouped rather than remembered. `guard_clobber()` exits
if a mock run would overwrite a file containing real rows (`--force` overrides).
`MAX_SPEND_USD = 20.0`. Mock output carries a banner at head and foot plus a
`### MOCK MODE - SIMULATED, NOT MEASURED ###` tag above *each* table, so a
cropped screenshot still carries it.

### Documentation

Four overlapping documents: `cascade_routing_initial_project_plan.md` (303 lines,
28 July), `cascade_routing_project_plan.md` (165 lines, v2.0, "replaces all
earlier plans"), `RUNBOOK.md` (210 lines), `README.md` (54 lines), plus

## 5. Open bugs the review already knows about — both reproduced

### 5.1 The oracle no longer bounds the cascade (`REVIEW.md` §3.10)

Confirmed. On math: cascade **100.0%**, oracle **98.3%**, always_expensive
98.3%. On a paired basis the cascade beats the oracle on exactly one task
(b=1, c=0) and beats always_expensive on the same one.

The cause is structural, not noise. `policy_oracle` picks the cheapest correct
option from `{cheap-greedy, expensive-greedy}`. Since the 3.1 fix, the cascade
has a third action available — cheap-majority-of-5 — which is not in the
oracle's action space. An oracle whose action space is smaller than the policies
it bounds is not an upper bound, and bounding headroom is its entire
justification.

### 5.2 The mock makes majority voting far too strong (`REVIEW.md` §3.11)

Confirmed exactly, on the 60 math tasks:

```
cheap greedy correct        : 44/60 = 73.3%
cheap majority-of-5 correct : 57/60 = 95.0%
self-consistency gain       : +21.7 points
```

Published self-consistency gains on competition math at k=5 are low single
digits. The cause is `models._wrong_answer`, which returns `truth + delta` for a
random delta 1–9, so wrong samples scatter across ~six distinct values while
correct samples all collapse to the identical truth string — plurality recovers
the truth whenever as few as 2 of 5 samples are right. Real models cluster their
errors, and that clustering is exactly why self-consistency is a weak confidence
signal, which is the mechanism the math half of the project exists to study.

Compounding it: `shared = _draw(task["id"], "shared", temperature, sample_idx)`
includes `sample_idx`, so per-sample correctness within a task is **independent**
rather than correlated. That is the second half of the same problem.

## 6. Things I found that are not in `REVIEW.md`

### 6.1 The pilot gate prints a verdict that contradicts its own band

`run_eval.py:164–169` branches on `fail < 0.20` → TOO EASY, `fail > 0.55` → TOO
HARD, else → `"GOOD - in the 30-40% target band where routing decisions
matter."` The current run prints:

```
cheap-model failure rate: 26.0%
  GOOD - in the 30-40% target band where routing decisions matter.
```

26.0% is not in the 30–40% band. The code's accept window is 20–55%; the plan,
the RUNBOOK table and this very message all say 30–40%. This is the project's
stated decision gate and it currently green-lights a value outside its own
criterion while asserting the value is inside it. In real mode this is the one
number that decides whether the task set is usable — it should not be able to
mislabel itself.

### 6.2 The code cascade runs the subprocess grader twice per task

`verify_code` calls `grade(task, response_text)`, then on acceptance
`policy_cascade` calls `grade(task, v.answer_text)` on the same string. I
instrumented `grade_run_asserts` and counted **2 subprocess launches for one
accepted code cascade task**. Not incorrect — `verify_code` returns what it was
handed, so the second grade always agrees — but it doubles the wall-clock cost
of the code half and is easy to remove by having the cascade trust the Verdict.

### 6.3 Cascade latency assumes serial self-consistency sampling

`verify_math` accumulates `latency += r.latency_s` across the k−1 extra samples.
Result: math cascade 2.30 s/task vs 0.90 s for always_expensive. The samples are
independent and trivially parallelizable, so the reported latency overstates a
realistic cascade by roughly 4× on math. If latency appears in the write-up it
needs either a `max()` instead of a sum, or an explicit note that it is the
serial worst case.

### 6.4 `REVIEW.md` §1's headline table is pre-fix and no longer matches
`results.jsonl`

| policy | §1 of REVIEW | actual `results.jsonl` |
|---|---|---|
| always_cheap | 68.0% | **74.0%** |
| predictive | 84.0% | **89.0%** |
| cascade | 93.0% | **99.0%** |
| oracle | 96.0% | **98.0%** |
| always_expensive | 95.0% | **98.0%** |

§3.10's numbers *do* match the file, so the review's own body is internally
inconsistent with its summary. This matters because §1 states the headline
finding — "code cascade 48% cheaper at identical accuracy, math cascade strictly
dominated" — and neither half survives the current numbers. Code cascade is now
**60%** cheaper ($0.001423 vs $0.003541) at identical 97.5%. Math cascade is now
*more accurate* than always_expensive (100.0% vs 98.3%) at marginally higher
cost, so it is no longer strictly dominated.

The uncomfortable part: the math result improved only because of the 5.2 mock
artifact. The fix made the headline number look better and its foundation
weaker.

### 6.5 The paired-statistics problem (§3.4) is worse than reported, not better

`REVIEW.md` cites cascade vs always_expensive at b=1, c=3 (four discordant
tasks). On the current results it is **b=1, c=0 — one discordant task**, and
oracle vs always_expensive has **zero**. Every other ordered pair has b=0: the
weaker policy is never right where the stronger is wrong.

That perfect nesting is a mock artifact of the 0.75 shared-latent draw. It means
paired tests would not merely be underpowered — they would be degenerate. The
review's suggested fix ("use McNemar, it's more powerful") does not rescue a
2×2 table with one off-diagonal cell.

## 7. Dependencies, config, and how to run it

**Dependencies.** Mock mode is pure standard library — `hashlib`, `json`,
`random`, `re`, `subprocess`, `tempfile`, `argparse`, `dataclasses`,
`collections`, `pathlib`. Real mode needs `anthropic`, imported lazily inside
`models._client()` so mock mode never touches it. **Nothing is declared
anywhere** — no `requirements.txt`, no `pyproject.toml`, no pinned Python
version. Bytecode suggests it has been run under both 3.10 and 3.13.

**Environment variables**

| var | default | effect |
|---|---|---|
| `ROUTER_MODE` | `mock` | `real` switches to live API calls |
| `MOCK_SEED` | `0` | reseeds the entire mock world; sweep it for run-to-run variance |
| `ANTHROPIC_API_KEY` | — | read by `Anthropic()` in real mode |

**The knobs that are actually decisions**

| constant | file | value |
|---|---|---|
| `SELF_CONSISTENCY_K` | policies.py | 5 |
| `AGREEMENT_THRESHOLD` | policies.py | 0.8 |
| `PREDICTIVE_HARD_LEVEL` | policies.py | 5 (selects 24/60 math) |
| `PREDICTIVE_CODE_CHARS` | policies.py | 100 (selects 14/40 code) |
| `MODELS` | models.py | Haiku 4.5 $1/$5 vs Opus 5 $5/$25 |
| `MOCK_SKILL`, `MOCK_FAILURE_CORRELATION` | models.py | cheap .86/.36, exp .97/.16; 0.75 |
| `MAX_TOKENS` | models.py | 2048 |
| `MAX_SPEND_USD` | run_eval.py | 20.0 |
| `CODE_TIMEOUT_S` | graders.py | 10 |
| `SEED`, `N_MATH`, `N_CODE`, `MIN_MATH_LEVEL` | build_taskset.py | 20260728, 60, 40, 3 |

**Commands**

```bash
python3 build_taskset.py     # data/ -> taskset.jsonl  (deterministic)
python3 sanity_check.py      # must print 40/40 and 60/60
python3 run_eval.py          # mock, free, ~seconds -> results.jsonl

pip install anthropic
export ANTHROPIC_API_KEY=...
ROUTER_MODE=real python3 run_eval.py --limit 10   # PILOT FIRST
ROUTER_MODE=real python3 run_eval.py              # full run
```

Also available: `--domain math|code`, `--force` (let a mock run overwrite real
results).

**What a full real run actually costs.** I instrumented `models.call` over the
whole taskset: a full run is **796 API calls — 602 cheap, 194 expensive**. The
cheap side is dominated by `verify_math`'s 4 extra samples on 60 math tasks (240
calls). The mock's modelled total is $0.95, but that uses fixed synthetic output
counts (80/120 tokens), so it is a floor rather than an estimate. The $20 cap
has plenty of headroom either way. `.claude/settings.local.json` allowlists
exactly the four commands above.

## 8. Summary

`llm-routing-comparison` is a one-day-old, ~1,200-line Python experiment
comparing cascade routing against predictive routing on 100 objectively-graded
tasks — 60 MATH500 problems where the cascade's verifier is a noisy
self-consistency guess, 40 MBPP problems where it is free and perfect. The
verifier asymmetry, not the router, is the manipulated variable, and that is a
genuinely good idea. The engineering around it is careful in ways most portfolio
projects are not: hash-seeded reproducible mocks, correlated tier failures,
router-visible features fenced into their own field so the leak cannot creep
back, a spend cap in code, provenance stamped on every result row, and
mock-mode output that labels itself as simulated on every table.

Where it stands: the pipeline runs end to end and I verified it — the task set
rebuilds byte-identically, both graders score reference answers 40/40 and 60/60,
and `run_eval.py` reproduces the committed `results.jsonl` exactly. But it has
never made a single API call. Every number in the repo is simulated, the
headline deliverable (`plot.py`) does not exist, and there is no git repository
at all, so for a project whose artefact is meant to be a GitHub page there is
currently nothing to link. Two known bugs are live and I reproduced both: the
oracle no longer bounds the cascade because the cascade gained a
majority-of-5 action the oracle cannot take, and the mock's scattered wrong
answers make self-consistency worth +21.7 points when the real figure is low
single digits. I found four more the review misses — the pilot gate prints "GOOD
- in the 30-40% band" at a 26% failure rate, the code cascade launches the
subprocess grader twice per task, cascade latency is summed as if the k samples
were serial, and `REVIEW.md`'s own headline table is pre-fix and now
contradicts both `results.jsonl` and its own §3.10. The RUNBOOK is stale enough
that following it from the top means redoing finished work and hunting for
constants that were renamed.

Obvious next moves, cheapest first: `git init` and push, with a
`requirements.txt` and `.gitignore` — thirty minutes and it unblocks the whole
premise. Then fix the mock's wrong-answer clustering and widen the oracle's
action space, because until both land no math number is worth plotting and the
current math result looks good only because the mock is generous. Then run the
10-task pilot, which is the real gate and the one thing that converts this from
a simulation into a measurement. Reconcile the three documents down to one after
that, not before, since the numbers will move again. And when the write-up
happens, the honest framing is a controlled replication with 2026 models in
which verifier quality is the variable — `REVIEW.md` §4 is right that the
"nobody has answered this" line is no longer safe, and being corrected on it in
an interview costs more than conceding it up front.
